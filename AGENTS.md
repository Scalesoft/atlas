# Rules for contributors and coding agents

These rules apply to every change, by people and by AI coding agents. [CONTRIBUTING.md](CONTRIBUTING.md) has the process.

# UI components and layouts

Before adding UI, review the development gallery at `/?gallery=1` on the frontend Vite server and its executable examples in `src/Atlas.Web/src/components/dev/ComponentGallery.vue`. The gallery is development-only and uses local sample data.

The gallery includes live examples of shared UI and layouts, plus an automatically populated, searchable source catalog of all existing Vue components. Feature screens in that catalog are references, not components to mount without their application context.

- Prefer an existing component, its supported variant, or a composition of existing components. Check local implementations before reaching for upstream shadcn examples.
- Evaluate the intended use case before choosing or creating a component: what user task it supports, how it is used at existing call sites, and which interaction and states it owns. Search by purpose as well as by name. Do not create another component for an already covered use case merely because its name, wording, or appearance differs; prefer reuse, composition, or a small compatible extension. A new shared component needs a genuinely distinct responsibility or a concrete incompatibility with existing ones, and its gallery example must explain when to use it versus the closest existing alternative.
- Reuse the demonstrated layouts: page with sections, overview cards, list rows, dialog, and settings shell with section navigation and a step flow.
- Progressive disclosure and StepFlow operate at different levels: disclosure handles dependent fields; StepFlow separates meaningful phases such as entry, impact review, and confirmation. Disclosure may be used inside a step with the same field components and validation rules. Do not introduce competing navigation patterns for the same use case. Compare the inline network example in `#/gallery/layouts` with the phased example in `#/gallery/settings/networks`.
- For complex settings with dependent choices, prefer progressive disclosure on one page (gallery: „Postupně odkrývaný formulář“): show the primary choice first, reveal only relevant dependent fields beneath it, retain earlier choices for editing, and keep a live summary or preview where useful. Put secondary options in a clearly labelled advanced section. Preserve compatible values when a parent choice changes; invalidate incompatible dependent values so hidden branches neither affect submission nor block validation. Save explicitly. Compose existing ChoiceCards/OptionPills, SettingsRow, InlineReveal and SettingsSection; use StepFlow only when distinct phases need Back/Next navigation.
- If a new shared component or reusable layout is necessary, briefly explain why the existing building blocks do not fit and add an example to the gallery in the same change. Keep examples current when changing existing components.
- Import real application components in examples; do not maintain gallery-only copies. Show relevant states and accessible labels. One-off private helpers do not need gallery entries.
- Keep the gallery lightweight: no separate component framework, backend calls, or persisted demo data. Shared primitives live in `components/ui`, application components in `components`, and settings compositions in `components/settings` under the frontend source directory.

# Interaction, motion and layout

One contract for every surface. Motion tokens are in `src/Atlas.Web/src/motion.css`; widths are the tokens in `src/Atlas.Web/src/styles/refresh.css`. The gallery shows the states live (`#/gallery/controls` „Stavy“, the responsive and dock examples) and `tests/browser/interaction-consistency.spec.ts`, `motion-lifecycle.spec.ts`, `responsive-workspace.spec.ts` and `responsive-settings.spec.ts` pin them. Check a change at 1280, 1440, 1920, 2560 and 3440 px, at 390 px where the screen exists on a phone, with the sidebar and the page dock both open and closed, and under reduced motion.

- **Every text of every object is Markdown**: titles of pages, boards and notes, contact names, requirement and event titles, labels, frame and group names, table cells, chart titles. Multi-line fields use the page editor's full Markdown; single-line fields use its single-line (inline) variant (bold, italic, strike, code, link, mention — no blocks). Edit in place with the page editor and its shortcuts; store Atlas Markdown; use the plain-text projection for search, sorting, `<title>`, notifications and exports. Identifier fields (e-mail, phone, URL, ticket ID) keep their own validation.
- **Nothing appears or disappears abruptly.** Content that enters rises `--atlas-rise` and fades (slow; lists stagger 40 ms, first eight: `.atlas-stagger` or `--st-stagger`). Disclosure animates height and opacity (`InlineReveal`). A dock or drawer slides from its edge. A dialog grows from .98 behind a dimming backdrop in 200 ms and leaves in 160 ms on the same curve; the search palette unfolds from its trigger and leaves in exactly those times. Tabs slide their indicator and only cross-fade the content. A loading state that replaces content waits `--atlas-motion-defer` first, then fades. An animation that is reversed midway continues from where it is. Reduced motion keeps a fade of at most 160 ms; it never snaps.
- **Hover never moves or resizes its target.** No lift, no size, weight, border-width or padding change, no text that re-wraps or truncates differently; actions revealed on hover have their room reserved or sit over the row. Cards and tiles answer with border colour and shadow (`--refresh-card-shadow-hover`, `--st-hover-shadow`); list, tree, table and menu rows with background and colour; a decorative child (an arrow, an icon) may nudge. Press is `scale(--atlas-press)`. Hover styles sit in `@media (hover: hover) and (pointer: fine)`; a disabled control has none and does not react to a press.
- **Focus is always visible and never animated:** `:focus-visible` with a 2 px accent outline (offset 2 px, or −2 px inside a clipping container).
- **Only tokens:** durations and easings from `motion.css`, never literals, never `transition: all`. Animate `transform`/`translate`/`scale`, `opacity` and colours; avoid animating a property that makes a long document reflow every frame.
- **Widths follow the room, not the screen.** `.workspace-content` is the container `workspace-content`: what lives in the workspace adapts with `@container workspace-content (max-width: …)`, so it is right with the sidebar or the dock open or closed. Viewport media queries are for the shell only (phone 680 px, drawer sidebar 1024 px). Page frames (Knihovna, a space, settings, profile) are centred and capped by `--atlas-page-max` with `--atlas-page-gutter`; forms and prose inside keep a readable measure. A component that depends on its own room uses a container query on its root. Long names truncate with an ellipsis and a `title`; nothing causes a horizontal scrollbar.
- **The page dock** (`WorkspaceSidePanel`) sits beside the article while the workspace leaves the article 600 px, floats over its right edge when it does not, and covers the screen on a phone; the reader's chosen width survives a temporary squeeze.
- **Fast first.** The shell and the article text render before secondary data (connections, readership, history, AI). A fast response never flashes a skeleton. Images reserve their box. Rows outside the viewport of a long list or tree are not rendered or use `content-visibility`.

# Build and images

- Release images are **Linux AMD64** (`linux/amd64`, .NET RID `linux-x64`); CI runs on GitHub-hosted `ubuntu-latest` runners and developer machines may be ARM64. These are separate architectures.
- Keep the Dockerfile SDK stage on `$BUILDPLATFORM`, including Wolverine code generation, and cross-publish with `--os linux --arch "$TARGETARCH"`; build the release image with `--platform linux/amd64`. Never run the .NET SDK under emulation.
- Separate SDK, NuGet, pnpm and image-build caches by build OS/architecture and target where applicable.
- Do not add arbitrary GC heap limits, lower test parallelism, or raise hang timeouts to hide a failure. Capture exit codes and memory diagnostics, fix the evidenced cause, and repeat only the failing test. One successful rerun does not establish the cause of an intermittent failure.

# Branches and releases (Vydání)

- `feature/*` (or a fork) → pull request into `develop` → `develop` is merged into `main`. A push to `main` is a release: `.github/workflows/release.yml` runs the CI jobs, tags `v<version>`, creates the GitHub release and publishes `ghcr.io/scalesoft/atlas` to GHCR; `ghcr.io/scalesoft/atlas-postgres` is published by `.github/workflows/postgres-image.yml` under the tag `docker-compose.yml` pins, only when `deploy/postgres` changes. It deploys nothing; installations pick a released version themselves. A hotfix starts from `main` and is merged back into `develop`.
- Every pull request needs green CI (`.github/workflows/ci.yml`) and the approval of a code owner (`.github/CODEOWNERS`).
- A release bumps the version on `develop` (`node tooling/release-version.mjs bump <patch|minor|major> version.json`, the same version in `Directory.Build.props` `VersionPrefix` with an empty `VersionSuffix` and in `src/Atlas.Web/package.json`); `release.yml` refuses a `main` whose three versions differ or carry a suffix. Right after the release `develop` opens the next development version: `VersionPrefix` the next version and `VersionSuffix` `dev`, web `<next>-dev`, a new unreleased CHANGELOG section (`version.json` keeps the last released version).
- The changelog is grouped by named version: a minor or major release is `## 3.6 · Codename` (`(nevydáno)` until released) with its notes, and each patch release adds its `### 3.6.1 — <date>` section at the end of that `##`, its own sections `####`. `tooling/release-notes.test.mjs` fails the build on a patch outside its `##`, and „Co je nového“ shows patches the same way, smaller beneath their named version (whatsNew/releaseNotes.ts `groupReleases`).
- Every release has user-facing notes „Co je nového“ in `src/Atlas.Web/release-notes/<version>.md`: draft them from the commits since the last tag (`node tooling/release-notes.mjs`) and rewrite them for users (`tooling/release-notes.test.mjs` fails without them); the GitHub release carries the same notes. Every major release is named and every minor release should be: the codename is two words that start with the same letter, the second one a fruit, and the letters go through the alphabet from one named release to the next (Performant Pear, Quiet Quince, Radiant Raspberry, Shared Strawberry, then T); a patch release has no name of its own. A named release also gets a wireframe mark of its fruit in the Bloom style: the notes open with `codename: …` and `mark: <name>` lines and have a `### Hlavně` section (one sentence, up to six (a major release: twelve) `- **Název** `klíč`: popis` highlights for the splash after the update), and `tooling/brand/<name>-mark.mjs` (a copy of `pear-mark.mjs` with its own geometry for `wireframe-mark.mjs`) writes `src/Atlas.Web/src/assets/brand/<name>.svg`; the same test requires it for minor and major releases, not for hotfixes.
- Never show or test a build under a version it is not: before presenting or testing a local instance, check that `/api/setup/status` reports the build under test, and stop stale dev servers. A reverse proxy in front of an installation should negotiate HTTP/2 ([docs/operations.md](docs/operations.md#https-za-reverzní-proxy)).
- Nothing company-specific goes into this repository: no internal hosts, credentials, customer data or deployment configuration. Company needs become configuration or a generic feature. Test data uses `example.test`.

# Data migrations (Migrace dat)

Follow [docs/background-jobs.md](docs/background-jobs.md#migrace-dat-mezi-verzemi). A FluentMigrator migration changes the schema and makes only the quick data changes the new code needs at once. A slower or content-wide data conversion is a background job that the migration requests with a queued `JobRun` row. It runs in short checkpointed batches while the application runs, so the code reads both data shapes until it ends. It stays in the product as an idempotent rebuild from the current state that an administrator can run again from Úlohy; only a one-off conversion from an old shape is removed, in the next release. Each such job has a server test over existing rows, including a second run that changes nothing.

# Editor (Atlas.Markdown)

- The editor is part of Atlas: the package `src/Atlas.Markdown` (`@atlas/markdown`, in the `src/Atlas.Web` pnpm workspace) and the library `src/Atlas.Markdown.Sync` with `tests/Atlas.Markdown.Sync.Tests`, history included ([docs/markdown](docs/markdown/README.md)). There are no separate editor releases or packages; change the editor in the same commit as its use.
- Atlas imports the editor's built `dist`; `pnpm run build:editor` rebuilds it when its sources changed (the test scripts, `pnpm dev`, CI and every publish run it). `ATLAS_EDITOR_MODE=source` serves the sources with hot reload.
- Run pnpm only from `src/Atlas.Web` (`pnpm --filter @atlas/markdown run typecheck`, `pnpm --filter @atlas/markdown exec vitest run --configLoader runner <file>`): inside `src/Atlas.Markdown` pnpm finds no workspace and installs it as a separate project with its own lockfile.
- Editor components follow [the editor's UI/UX decision and component inventory](docs/markdown/decision-editor-component-ui.md): selection-owned toolbars above the component, anchored settings panels, shared theme tokens, keyboard and focus behaviour, readonly, draft cancellation, independent undo steps and lazy loading boundaries. Action and choice context menus have no visible title or close button.
- The editor's contracts: `node src/Atlas.Markdown/tests/contracts/architecture.mjs` (entry boundaries, lazy Monaco and Scalar, the optional assist module) and, on a built dist, `node --test src/Atlas.Markdown/tests/package/bundle-budget.test.mjs`. Raising a budget is a decision recorded in the commit. `tests/changed.ps1` runs them with every editor change, and CI on every pull request.

# Testing (Testování)

Run the smallest check that proves the change. CI runs the full suites on every pull request and on `develop`; `main` releases.

- **Test database.** Start one throwaway PostgreSQL 19 with pgvector in Podman or Docker, on tmpfs, and point `ATLAS_TEST_CONNECTION` at it (`ATLAS_TEST_DATABASE` defaults to it). The official multiarch pgvector image is pinned by digest; releases and CI run the Alpine (musl) image from `deploy/postgres` instead, which sorts text differently (`deploy/postgres/collation.sql`). This local database is glibc, so an order-dependent test must also be run against `atlas-postgres` (build and start it as in `deploy/postgres/README.md`) before it counts:
  ```powershell
  podman run -d --name atlas-test-pg -p 127.0.0.1:55450:5432 -e POSTGRES_PASSWORD=atlas -e POSTGRES_DB=atlas_test --tmpfs /var/lib/postgresql:rw,size=8g docker.io/pgvector/pgvector:0.8.7-pg19-trixie@sha256:ace863afa68a13560603dc7366fad0adb4f5ddd0a21c8f06418195f32e03fa08 -c max_connections=500 -c fsync=off -c full_page_writes=off -c shared_buffers=512MB
  $env:ATLAS_TEST_CONNECTION = 'Host=127.0.0.1;Port=55450;Username=postgres;Password=atlas;Database=atlas_test'
  ```
  Migration 2026100520 requires pgvector, and the fixtures refuse a server without it (an older `atlas-test-pg`, from the plain `postgres:18.6` image or PostgreSQL 18, must be removed and started again with the command above). Keep `synchronous_commit` at its default; a test asserts it. `fsync=off` and `full_page_writes=off` are part of the recipe, not an option: with fsync on every commit waits for the disk and every `DROP DATABASE` forces a checkpoint the other fixtures queue behind (the server batches took 1400 s against 764 s, and a run on many cores failed at random on `too many clients`). The fixtures refuse a server with fsync on and say how to fix it; `ATLAS_TEST_DISPOSABLE_SERVER=1` lets the run switch it off itself (`ALTER SYSTEM`), which is what `tooling/ci/server-tests.sh` does for the throwaway database container of the CI job. Set it only for a server that holds nothing else. Start the `atlas-postgres` image the same way (`localhost/atlas-postgres:…` with the same `-c` settings and tmpfs). A native Windows PostgreSQL is rejected with a clear error: new backends and `CREATE DATABASE` are far too slow for database-per-test fixtures. The role needs CREATEDB, because every fixture gets its own database cloned from a migrated template (`tests/Atlas.Server.Tests/Platform/TestDatabases.cs`).
- **How a test gets its database and host.** Only from the shared fixtures in `tests/Atlas.Server.Tests/Platform`: `AtlasTestHost.CreateAsync("prefix_")` (handlers, no HTTP), `AtlasHttpSite.CreateAsync("prefix_")` (the real pipeline) or `DisposableSchema.CreateMigratedAsync` (SQL only). `AtlasTestHost.CreateAsync("prefix_")` without a configuration of its own is the one shared host of the process on one shared database: a test there keeps to users and spaces it seeds itself (`SeedUserAsync` gives the login a unique suffix; a fixture that saves accounts itself uses `TestLogin.For("writer")`), never counts a whole table, and never changes the schema or stops the host. A test that must do one of those takes `AtlasTestHost.CreateIsolatedAsync` with the reason beside the call; the guard lists the files that do. `AtlasHttpSite.CreateAsync("prefix_")` is the one shared site in the same way (`shared: true` shares one site per constant settings, `sharedAs: "name"` one host or site per fixture whose services are the same for every test): `CompleteSetupAsync` signs the client in as a wiki administrator of the test's own, `OwnSpaceAsync` makes its space, and a test never works in the first space the installation lists. Exceptions are for a schema version or upgrade, the first start, DDL, stopping the host, and a row the whole installation shares; `docs/testing/isolated-tests-4.1.0.md` lists them. Every other fixture gives a clone of the template that is migrated once per test process (`TestDatabases`; a clone costs about 30 ms and its drop 100 ms on the database above) and dropped with the fixture. Create one fixture per test, or share it among the tests of a class when they only read; do not start a second host for what the first one can answer. An empty database (`DisposableSchema.CreateAsync`, `CreateEmptyAsync`: every migration applied by the test) is for migration and upgrade tests. No test runs `CREATE DATABASE`, builds its own `WebApplicationFactory` or host, or keeps a database of its own: `TestFixtureCostConventionTests` (a guard) fails on it. `ATLAS_TEST_COSTS=<file>` makes each test process write what its fixtures cost (databases, hosts, time per step, peak memory) to `<file>.<pid>`; CI prints it with the duration of every batch. A reset-and-reuse pool of databases was measured and rejected (`docs/testing/test-speed-4.1.0.md`): an honest reset truncates all 159 tables (0.5 s), more than a clone and its drop cost without fsync.
- **While working:** `pwsh tests/changed.ps1`. It runs only what the change since `origin/develop` touches: the server tests of the touched feature folders (Smoke for shared code), vue-tsc and `vitest --changed`, in parallel. It builds without analyzers and code style (half the incremental build time); `smoke.ps1` and `full.ps1` build with them, and switching back recompiles, so nothing is skipped at the end. Single tests by hand:
  ```powershell
  dotnet test tests/Atlas.Server.Tests -c Release --filter "FullyQualifiedName~Vaults"
  pnpm --dir src/Atlas.Web exec vitest run src/components/admin/VaultsPanel.test.ts
  ```
- **A quick check while developing, when you want one:** `pwsh tests/smoke.ps1` (server tests tagged `Smoke`, vue-tsc and a vitest subset, in parallel, about 40 s). A development aid, not a gate.
- **CI runs the full suites** (`.github/workflows/ci.yml`: the release tooling tests, editor and web, then the server suite with the migration tests in batches and the Markdown Sync, Yjs and YouTrack tests through `tooling/ci/server-tests.sh`) on every pull request and on `develop`, and again before `release.yml` tags and publishes anything; a red run publishes nothing. Do not run or wait for a full suite locally before opening a pull request; push and let CI run it.
- **A migration comes with its test.** Every database migration is a new migration (never edit a released one) with a test in the server suite that runs it over existing rows (pattern: `FluentMigrationTests`). CI runs these tests and they are the automatic gate for data.
- **Development tools, not part of CI or of a release:** `pwsh tests/full.ps1` runs every suite at once (server, YouTrack, vitest, vue-tsc and the mocked settings browser specs `settings-p3`/`settings-real`/`settings-security` on a Vite dev server), then `tests/browser/e2e-podman.ps1`, whose batches run at the same time, one pod each (`-SkipE2e` leaves the browser tests out). `tests/upgrade/upgrade-podman.ps1` runs the data of a released version through the new build ([docs/operations.md](docs/operations.md#test-upgradu-dat-vývojový-nástroj)). Reach for them for a release-wide refactor, UI flows across pages or a migration of existing data.
- **Never rerun a full suite for a small follow-up fix.** Rerun the affected tests (`tests/changed.ps1`). The result cache of `tests/full.ps1` repeats only the parts a fix touched.
- **No full suite during the work.** Not after each step, not to confirm a fix; CI runs it on the pull request. To check an intermittent failure, repeat only the failing test or file (`--filter`, a single vitest file) several times in one command; never repeat the whole suite and never delete `artifacts/test-cache` to force a rerun.
- **Caches.** `tests/smoke.ps1`, `tests/changed.ps1` and `tests/full.ps1` remember each part that passed together with the state of its inputs (`artifacts/test-cache`). While the inputs stay the same, the part reports CACHED instead of running again. `e2e-podman.ps1` reuses its previous publish until `src/` or the build files change (`-Republish` forces a new one). The login throttle counts only failures, so the batches need no pause. vue-tsc is incremental (`node_modules/.cache`), and the scripts run vitest with `--experimental.fsModuleCache` (a quarter to a third faster; `vitest --clearCache` if it ever misbehaves). The persistent cache keys a module by its own content, so `vite.config.ts` keeps every module that uses `import.meta.glob` out of it (a glob depends on the directory listing, and Vitest itself skips only the untyped `import.meta.glob(` form).
- **Hangs fail fast.** Every `dotnet test` of the server tests uses `tests/Atlas.Server.Tests/test.runsettings`: a test still running after 5 minutes aborts the run, and VSTest prints its name under "The test running when the crash occurred:" (no dump is written). `tests/smoke.ps1` uses 2 minutes. Fix a reported hang; do not raise the limit.
- **Parallelism stays at the CPU maximum:** xUnit `maxParallelThreads: 0` (processor count) with server GC and Wolverine handlers compiled once per build (`SharedHandlerCompiler` keeps the assemblies under `%TEMP%/atlas-test-handlers/build-<stamp>`, so only the first process after a build compiles them), vitest `maxWorkers: "50%"` (measured optimum: 16–32 workers on 64 threads), `dotnet build -m`. When something does not scale, fix the shared resource (database, port, file, lock) instead of lowering parallelism. Playwright stays at one worker, because its specs share one host, one synthetic account and the login throttle.
- **Every new test needs a reason.**
  - Test a behaviour once. Put rules in the handler test. An HTTP test covers only what HTTP adds: routing, binding, serialization, CSRF, headers, status codes.
  - Pick two or three representative cases, not an exhaustive matrix.
  - Do not test trivial mappings or DTOs. Do not copy canary assertions (401, CSRF 400, no-store) into every feature.
  - Tag `[Trait("Category", "Smoke")]` only on one or two critical-path tests per feature.
- **Editor schema.** The server stores only rich documents the editor opens (400 `invalid_document` with the JSON `path`). Validation is owned by the editor: `Rules.ValidateDocument` calls `MarkdownDocumentValidator.Builtin` of `Atlas.Markdown.Sync` (`src/Atlas.Markdown.Sync`), which embeds the editor's manifest `src/Atlas.Markdown/schema/markdown-schema.json`, and the collaboration guard (`AddAtlasMarkdownContentGuard`) uses the same manifest. The editor's `src/schema/manifest.test.ts` generates the manifest and the verdict corpus in `tests/Atlas.Markdown.Sync.Tests/Fixtures` (`ATLAS_UPDATE_SCHEMA=1`); a schema change in the editor regenerates both in the same commit. Atlas keeps only its own wording (`Platform/Validation/EditorDocumentErrors.cs`, Czech reason per stable violation code) and its own rules (secret references, size limits, attachment ownership); `EditorDocumentValidationTests` checks the plugin set Atlas binds and the documents Atlas itself writes. A content plugin outside the built-in thirteen needs a host manifest (`describeMarkdownSchema` in a web test, `MarkdownSchemaManifest.Parse`) instead of `Builtin`.
