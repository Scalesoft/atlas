# Saved working revisions in search

The MVP search filter must find accessible saved drafts without returning another writer's private, never-published page. The published query remains the default and its public SQL constant remains byte-for-byte equivalent. `SearchOptions` is an additive overload; the old call signature forwards to defaults. HTTP filters are `content=published|drafts`, `changedWithin=any|day|week|month`, and `sort=relevance|published`. In draft scope latest ordering means the saved working change time. Unknown choices return 400.

## Evidence and choice

A scan of 1,000 saved drafts with roughly 5 KB operational text per page took 976–1,253 ms per request. Narrowing the materialized stages and computing each vector once still took 769–1,199 ms. Both probes had pooling disabled by the test connection helper; the second artifact's original filename incorrectly suggested otherwise. With pooling explicitly enabled, the initial indexed query took 96 ms for the common term, 68 ms for the technical term and 530 ms for the absent term. The absent query's database plan alone took about 497 ms, demonstrating a query cost independent of connection setup. Artifacts preserve their original filenames and now record the corrected pooling configuration.

An indexed, rebuildable current-revision read model avoids normalizing every visible draft on every query. No business history, ownership or permission rules change. Functional indexes alone cannot avoid recomputing vectors for ranked matches, and marking dictionary-dependent functions immutable would be incorrect.

## Domain and persistence model

`Page` remains the durable identity; `PageRevision` remains authoritative immutable saved content with its existing half-open UTC validity intervals. A page has zero or one `WorkingSearchDocument`; each projection pins exactly one revision belonging to that page. It may describe a current revision identical to publication: the query explicitly excludes that state from draft results. This makes publication and page moves independent of projection maintenance.

`WorkingSearchDocument` is a plain mutable derived read model, like existing `SearchDocument`, without temporal history or soft deletion. Exact columns:

- `PageId uuid`: explicitly named primary key and FK to Page, cascade on physical deletion.
- `RevisionId uuid`: required; composite FK `(PageId, RevisionId)` to PageRevision `(PageId, Id)` pins the source revision. The PageId primary-key index covers lookup of that single child for FK maintenance.
- `NormalizedTitle text`, `NormalizedBody text`, `Vector tsvector`, `HeadingVector tsvector`, `Headings jsonb`, `ChangedAt timestamptz`: required, generated by database trigger from the pinned current revision. Headings must be a JSON array. ChangedAt equals the revision's UTC ActiveFrom.

There are no speculative IDs, flags, actors or alternate timestamps. Raw title/body and space identity are not duplicated: queries obtain them from the pinned revision/page. A GIN index covers Vector; trigram GIN indexes cover normalized title/body, with fastupdate off as in the existing published projection. HeadingVector is used only for ranking, so it needs no separate index. A ChangedAt index supports date/latest filters. No NHibernate entity or mapping is needed for this SQL read model.

After a PageRevision is inserted or its current interval/content changes, the same transaction upserts the projection for a current row or removes a projection still pointing to a closed row. A before-write projection trigger computes all derived columns and persistent heading metadata using existing normalization and heading extraction functions. Positional gaps between title, headings and body preserve quoted phrase boundaries. Dictionary-dependent functions retain their existing volatility declarations.

Migration 026 creates the table/functions/indexes, backfills current revisions, and analyzes the projection. Closing/inserting versions, restores and imports already pass through PageRevision; failed writes roll back source and projection together. A rebuild is an upsert of each current `(PageId, RevisionId)`; stale extra rows are removed by comparison to current revisions. This read-model migration follows the existing irreversible embedded migration convention; source history makes rebuilding or dropping only the projection possible. No migration runs against the user's host in this task.

## Retrieval and validation

Queries join projection to the exact current PageRevision and current Page, exclude trash and current=published, and apply current account/stamp, effective Writer-or-higher role, private ownership and date filters before ranking/LIMIT/OFFSET. Permission-dependent values never enter the projection. Snippets and heading anchors come only from authorized selected revisions. Published aliases stay in published search.

Verification proceeds through failing behavior tests, then migration/transaction tests: initial create and save refresh, closed revisions disappear, rollback leaves the old projection, rebuild/backfill, publication/draft transitions, current group/stamp revocation, own/other private draft, trash, phrase boundaries, heading relevance, date/order/pagination. Repeat the same 1,000-draft timed probe with pooling, then review DB/security/query plans and run the existing published baseline unchanged.

## Measured query behavior

The final draft query unions indexable full-text, title-prefix and fuzzy candidate IDs. Fuzzy branches exclude IDs already matched by full text or prefix: `A ∪ C ∪ (¬(A ∪ C) ∩ B)` equals `A ∪ C ∪ B`. This avoids decompressing every matching body twice without changing relevance, latest ordering, fuzzy semantics or pagination. Current ACL checks still precede ranking and every limit that determines returned results; the bounded strategy probe described below exposes no result data. No query planner settings or corpus caps are used.

The isolated PostgreSQL 18 probe uses 1,000 saved drafts with approximately 5 KB bodies, explicit Npgsql pooling, an analyzed projection, and 20 sequential requests per query in each sort mode. It is distinct from the specification's 10,000-page/20-reader published-search workload. Before the dense-match optimization, p95 milliseconds (relevance / latest) were: common term 87.58 / 78.00; technical term 79.51 / 80.31; absent term 3.50 / 3.56; fuzzy-only body typo 582.86 / 571.49. That last case failed the 300 ms backend target and motivated the following change. Its raw samples and plans remain in `artifacts/quality/draft-search-final-repeated-pooled.json` as pre-optimization evidence.

The follow-up performance change keeps the same persistence model. A bounded index probe of 64 non-primary body matches chooses execution strategy, never returned result count. Fewer than 64 matches exhaust that branch under the statement's single MVCC snapshot; otherwise the query sorts current authorized candidates by their exact final fuzzy-only score and latest/title/ID keys, then checks body matches in that order until `offset + take` results are found. The `OFFSET 0` subquery boundary keeps body evaluation after the cheap sort. Each union branch needs at most the first `offset + take` rows in the same total order: any omitted row already has that many distinct predecessors in its own branch, even if branches overlap. No permission or result is inferred from the probe. The 64-row threshold bounds the dense-case probe cost while retaining indexed sparse/negative lookup; it is an internal execution choice, not a product or corpus limit. Verification adds dense mixed primary/body/title-fuzzy overlap, hidden private rows, deterministic ordering and later pages for both sort modes, followed by the unchanged 160-request probe.

The final unchanged probe measured p95 milliseconds (relevance / latest): common 74.20 / 65.38; technical 69.65 / 65.11; absent 3.33 / 2.92; fuzzy-only body typo 105.04 / 102.15. Creating/saving approximately 5 KB took 100.59 / 29.92 ms. Every measured mode meets the 300 ms backend target. Actual fuzzy plans show the bounded 64-row probe and 21 body checks through the projection primary key, rather than 1,000 body checks; total EXPLAIN execution was 138.86 / 138.24 ms. These sequential measurements do not claim an all-workload SLA or browser end-to-end latency.
